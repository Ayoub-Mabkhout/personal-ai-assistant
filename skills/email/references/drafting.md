# Drafting in the user's voice

Retrieve current preferences from the private profile, not from public skill text.
Use the actual exchange to determine what must be answered and what was agreed.
Where live authorized sent-mail tools exist, find up to three suitable messages
written by the user to comparable recipients. Avoid caching those examples in the
repository, logging unrelated examples, or making a universal style rule from one
message. Source availability may be limited in an attachment-only local archive.

Adapt the draft to the audience: colleagues/researchers, university administration,
landlord, customer support and formal applications may call for different wording.
Match useful choices—opening, directness, paragraph length, detail, question format,
sign-off—while preserving the current request's facts and language. Don't invent
deadlines, availability, legal positions, credentials or promises. If the original
question depends on another thread, resolve that context before composing.

Prefer a clear request or answer early. Remove generic praise, empty politeness,
formulaic introductions and repeated closing lines when the user's preferences
don't call for them. Keep necessary nuance and diplomatic wording. Do not apply
casual language indiscriminately to formal correspondence.

When drafting a reply, identify the reply target and thread. Include the attachment
list when relevant, and confirm each file exists and is the requested version.
Drafting is not sending. Explicit user send instructions authorize the specified
delivery; unclear recipient or missing essential facts require clarification.
Provider acceptance/message ID is execution evidence; an ambiguous send response
requires checking existing sent mail before retrying.
